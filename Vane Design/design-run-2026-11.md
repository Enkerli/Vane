# Vane: design run, November 2026

A brief for a design pass (a design agent, or a person). Read with `design_questions.md` (June) and the
generated inventory `parameters-2026-11.md`. The June run settled the structure (Stage on the left; Patch,
Matrix and Presets on the right; one WebView app for desktop and iPad). Since then a period of "mad scientist"
exploration added a reed model, a voice input, pitch tracking, an effect build and a room, each landing in the
panel where it fit at the time. The panel now works but is a mess. This run is about **converging**: fewer,
clearer surfaces, distinct presets, and controls that appear when they matter.

## What Vane is now
A personal performance instrument for wind controllers, MPE surfaces, keyboards, and now a voice or a control
voltage. One mono-capable voice engine with two sound sources:
- **Wavetable oscillator** (morph, pulse width, fold, inharmonicity, sync, noise; unison and rotating chords),
- **Reed models**: *WindCore* (the default: reed, cone and mouth with 27 character controls) and *MiniSax* (older),
then a filter, a vowel (formant) filter, a transient (attack sample) layer and a room. A 24-slot modulation
matrix connects sources (breath, expression, MPE pressure, slide, pitchbend, velocity, keytrack, 8 aux CCs,
voice vowel, level and brightness, two input channels as control voltages) to destinations.

Builds: AU, VST3, CLAP, Standalone (macOS); AUv3 and Standalone (iPad); VST3 and LV2 (Linux); a browser
version (no audio input there yet except the microphone, WindCore and MiniSax). **Vane FX** is the same plugin
as an effect, with an audio input. Panel source: `music-suite/apps/vane/index.html` (vanilla JS, one file,
about 2700 lines), shared by the plugin and the browser.

## Where it hurts (observed)
1. **One group holds everything about the reed** (about 55 controls), including things that are not the reed:
   synthetic breath and the whole voice input.
2. **Three vowels** that look alike and are not: the global *Vowel* filter (any sound), WindCore's *Mouth* (its own
   resonances), and *Voice vowel* (your formants driving that mouth). Nothing explains which is which.
3. **Four breaths**: a controller's breath (CC2 / pressure via the breath macro), *Synthetic breath* (for
   keyboards), *Voice breath follow*, and *Input 1/2* as control voltages. They combine in ways the panel does
   not show (synthetic breath stands down once a real controller speaks; voice follow multiplies).
4. **Three attack noises**: WindCore's *Chiff* and *Key noise*, *Voice onset noise*, and the *Transient* layer.
5. **Two glides**: *Glide* in Performance (portamento between notes) and *Glide* as a Voice Pitch mode (following
   the sung pitch). Same word, different things.
6. **Irrelevant controls stay visible**: the oscillator group when a reed model sounds (only a note says so);
   MiniSax sliders when WindCore is chosen are hidden, but the synthetic breath shows for wind controllers that
   never need it; Voice controls show with no input.
7. **Host clutter**: 303 parameters reach the host's automation list, including 144 matrix fields and 50 older
   fixed-route amounts that only exist to translate presets from before the matrix.
8. **Presets**: the browser lists everything flat; the WindCore presets are not in it unless a tool is run; the
   best patches were found by playing and live in a user folder.
9. **No surface for routing**: whether notes and audio arrive (side chain, Vane FX, mic) is invisible until it
   fails; `docs/daw-setup.md` explains it in prose.

## How things interact (what a layout has to respect)
| This | Depends on / changes |
|---|---|
| Sound source | Oscillator **or** reed model, never both; the filter, vowel filter, transient layer and room apply to either |
| Reed model's loudness | Comes from breath (no VCA routing); the matrix's VCA routes only shape the oscillator |
| Breath | max(controller breath, expression, pressure, synthetic breath, velocity mix) × voice breath follow |
| Voice controls | Need an audio input; act on the reed model (WindCore; private builds: other models too) |
| Voice pitch | Plays the notes; host notes are then ignored; bend uses the host's pitch-bend range |
| Mouth (WindCore) | Set by Mouth shape/strength, or replaced by Voice vowel while a voice sounds; also a matrix destination |
| Tuning | MTS-ESP or internal tuning; voice pitch could snap to its degrees (not yet) |
| Chords / unison | Apply to the reed models too (one horn per voice) |
| Room | Last; works with anything; mix 0 is off |

## Directions to explore (a hypothesis to challenge, not a decision)
- **Order by signal flow**: *Input* (controllers, voice, control voltage: what plays it) → *Source* (oscillator or
  reed, with the model's own character) → *Shape* (filter, vowel, transient) → *Space* (room) → *Output*.
  Performance (mono, glide, tuning, chords) and Modulation run across.
- **An Input surface**, separate from the reed: which inputs are live (MIDI, breath, voice, CV), what each drives,
  the routing state (side chain present? mic on?), and the voice's settings. The Voice controls move here.
- **Progressive disclosure in three depths**: *Play* (the 6 to 10 controls that change the sound most, per source;
  for WindCore perhaps Air, Mouth, Embouchure, Response, Body, Bloom, Chiff, Vibrato), *Character* (the rest of
  the model's controls, in its five groups), *Deep* (calibration, legacy, rarely touched). Defaults collapsed.
- **Show only what acts**: hide the oscillator when a reed sounds; hide voice controls with no input (or show
  them greyed with "connect a voice"); hide synthetic breath once a breath controller is seen.
- **Name the duplicates apart**: e.g. *Vowel filter* (global) vs *Mouth* (reed) vs *Voice vowel*; *Portamento* vs
  *Pitch follow*; attack noise in one place with its sources.
- **Presets as the front door**: a small curated, bundled set that each shows one idea, by how it is played
  (wind controller, keyboard, voice, control voltage) and by character, with the rest a user library.
- **Host parameter list**: decide which parameters a host should see (likely: the Play depth of each section, the
  matrix amounts, not the 50 older routes).

## Constraints (unchanged)
Same UI on desktop (mouse) and iPad AUv3 (touch, small window, no hover or modifier keys). C++-sourced labels
ASCII only. Vanilla JS and SVG, no build step for the panel. Parameter ids and choice indices are forever (old
sessions must load), so reorganise the presentation, not the ids.

## What we would like from the design run
1. An information architecture for the Patch tab (or a replacement of it): sections, their order, what is shown
   at each depth.
2. The Input surface: what it shows, how it tells the player what is connected.
3. Names for the duplicated concepts.
4. The preset browser for a small curated set plus a user library.
5. Which parameters a host sees.
6. Mockups that can be built in the existing panel, iPad first, desktop second.
