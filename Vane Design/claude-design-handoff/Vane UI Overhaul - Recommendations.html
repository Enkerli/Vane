Vane · UI Overhaul Spec v1

Review & Recommendations

An assessment of the whole-app prototype against the locked overhaul spec — what's on target, where the prototype under-delivers on its own headline goals, and a prioritized path to close the gap.

Reviewing vane_app_prototype.html against vane_ui_overhaul_spec.md design source wireframe-styles.css · artboards/*

Bottom line

The direction is right and worth committing to. WebView rendering, a 24-slot generic mod backend mapped to APVTS param groups, the six-source colour system, and the two-column Stage / Inspector layout are all sound — and the prototype proves the mock-bridge validation harness (§9) works as intended.

But the prototype exists to solve two named pain points — precision and touch — and today it lands neither. There is no real dragging (clicking the track jumps the value), no fine-drag, no steppers; and every hit target is well under the 44 pt the spec mandates. Meanwhile the mod-matrix row has quietly dropped three things the spec's chosen design (MMStack) treats as core — attack/release, a per-route enable, and the live source meter — and the visual surface has drifted off the design tokens (10 px corners, no shadow) into something harder than the artboards.

None of this is a redesign. It's a completion pass: make the controls behave, size them for the iPad, restore the matrix row, and re-seat the look on wireframe-styles.css. The 18 recommendations below are grouped and prioritized to fold straight into the §10 build phasing.

A

Interaction & precision

The headline reason the overhaul exists. Spec §6 specifies four behaviours for every continuous control; the prototype implements one and a half.

A1

Replace click-to-set with real pointer drag

Blocker

Tracks use onclick → trackSet: a single click jumps the value to wherever the pointer landed. There's no pointerdown → pointermove drag at all. For a performance synth this is the worst case — one stray click on a track destroys a dialed-in cutoff, and you can't nudge.

Implement pointer-capture drag on every .track and .bipolar: pointerdown grabs, pointermove maps delta→value, pointerup releases. Keep tap-to-focus, but value only changes on drag. This is the foundation A2–A3 build on.

spec §6.1 · prototype trackSet() / slotAmtSet()
A2

Add a fine-drag precision mode

Blocker

This is explicitly called out in the spec as "the Bitwig-like win" and it is entirely absent. Without sub-step precision, the matrix amount and cutoff can't be set to the exact value a player needs — which is the original complaint.

Two routes to fine control: a modifier-held drag on desktop (Shift/⌥ → ~5–10× lower sensitivity), and a vertical slow-drag gesture that works identically on touch. Pair with a subtle "fine" cursor/affordance so it's discoverable. The typed field (already built) is the third precision path — keep all three.

spec §6.2 · §6.3
A3

Add ± steppers where space allows

Medium

Spec §6.4 lists a stepper affordance; none exists. For discrete-feeling values (Detune ¢, PB range st, Glide ms) a one-tap nudge is faster and more accurate than any drag.

Add compact −/+ steppers to typed-value rows on desktop, and expose ↑/↓ arrow-key nudge while a numeric field is focused (with units shown). On iPad, steppers double as oversized touch targets — see B1.

spec §6.4
B

Touch & cross-platform

The second named pain point. iPad AUv3 is a first-class target, but the prototype was built at desktop density and the single 760 px breakpoint only re-stacks columns — it never enlarges anything.

B1

Hit targets fail the 44 pt rule — add a touch density pass

Blocker

Measured against the spec's "≥ 44 pt on all interactive elements": slider tracks are 8 px tall, the slot delete is a 15 px glyph, .icon-btn is 30×30, segmented buttons ~24 px, selects ~30 px. On glass these are mis-hits waiting to happen.

Drive density from a CSS custom-property scale that the width breakpoint (and ideally a coarse-pointer media query) bumps: control height 32 → 44 px, track 8 → 14 px, font and padding up to match. Same React tree, CSS-only — exactly the model §7 prescribes.

B2

Build the iPad bottom tab bar & respect safe areas

High

§7 specifies a single-column stack with a bottom tab bar on iPad and respect for safe areas. The prototype keeps tabs pinned to the top of the inspector and has no env(safe-area-inset-*) padding — under the AUv3 home indicator the bottom row will be clipped.

At the narrow breakpoint, relocate [Patch][Matrix][Presets] to a fixed bottom bar with thumb-reachable tabs, and pad the shell with env(safe-area-inset-bottom). Header → Stage → active tab full-width above it.

spec §7
B3

Remove hover-only affordances

Medium

§7 says "no hover-only affordances." Several states are hover-gated: the typed-value editor's only affordance is .val:hover background, slot/preset borders only react on :hover. On touch there is no hover, so these cues never appear.

Make affordances always-visible or press-driven: a persistent edit underline on typed values, an explicit "edit" tap zone, and active/pressed states instead of hover-reveals. Gate any remaining hover polish behind @media (hover:hover).

spec §7
C

Mod-matrix completeness

The free matrix is the headline feature. The chosen design is MMStack (§4), whose route row is fully specified — but the prototype's row is a reduced version that drops slew and state controls that are central to Vane's slew-limited identity.

C1

Restore the full MMStack route row

High

The spec's row is: source dot + label + CC (picker) → arrow → dest (picker) → amount −1..+1 → curve {lin·exp·S} → atk / rel → live source meter → enable + delete. The prototype keeps source · dest · amount · curve · delete and silently drops attack/release, the live source meter, and a per-route enable.

Prototype row — 5 controls
Breath → Cutoff linexpS ✕
↑ no attack/release · no live meter · no enable (delete is the only off-switch)
Spec MMStack row — full
Breath · CC2 → Cutoff linexp± ↑5 ↓80 ✕
↑ CC picker · atk/rel · per-route meter · enable toggle restored

Bring the row back to parity with MMStack. Attack/release aren't optional polish — they're the slew limiting that defines how Vane responds to breath, and they appear in the DSP defaults table and every artboard. A separate enable lets a player mute a route without losing its settings (delete is destructive).

spec §6 · README mod-matrix defaults (atk/rel per route)
C2

Add the source-binding / CC# picker

Medium

CC labels (SRC_CC) are a fixed lookup. §5's macro bindings require Breath src ∈ {CC, AT, MPE Z} with a settable CC#, and Expr ∈ {CC, AT} + CC#. Players on a BC-1 vs a Sylphyo bind different CCs.

Make the CC chip on each source a small picker (binding type + CC number), surfaced both in the matrix row and a Macro-bindings group in Patch. Persist via APVTS like everything else.

spec §5 macro bindings
C3

Reconcile the curve set with bipolar routing

Polish

The prototype's curve segment is {Lin, Exp, S}, but the artboard and the README treat Slide→Cutoff as bipolar (±), and the amount slider is already −1..+1. It's ambiguous whether "±" is a curve or just a negative amount.

Decide and document: keep curve = shape {Lin, Exp, S} and let polarity live entirely in the signed amount (cleaner), or add an explicit bipolar curve. Whatever you pick, the segmented control labels must match the backend choice enum exactly.

spec §5 dests · README (slide → bipolar)
D

Visual-system fidelity

Spec §3 says to use wireframe-styles.css tokens verbatim. The prototype re-declares its own and lands harder and flatter than the artboards it's meant to consolidate.

D1

Re-seat radii, shadows & surfaces on the real tokens

High

The source design uses border-radius:20px panels with box-shadow:0 6px 22px rgba(28,25,20,.05), 14 px sub-panels and 14 px segmented controls. The prototype redefines --r:10px, --r-sm:7px and drops shadows entirely. The result reads as a generic flat plugin, not the warm, soft Vane surface in the artboards.

Prototype · 10px, flatTokens · 20px, soft shadow

Import the token file rather than re-declaring it. Bundle wireframe-styles.css variables as the single source of truth so design and build can't drift, then map component classes onto --vn-*. One change there re-themes the whole app.

spec §3 ("use wireframe-styles.css tokens verbatim")
D2

Make the visualiser the signature, not a generic sine

Medium

The Stage is the largest panel (1.5fr) yet shows four hardcoded scrolling sine paths. The artboards proposed far more: MainViewA's Breath / Spectrum / Pitch view switch with a live note + filter readout, and the "wind tunnel" flow. Right now the most prominent panel carries the least meaning.

Treat the visualiser as Vane's identity moment. At minimum: drive it from real breath/expression history, add the Breath / Spectrum / Pitch view toggle and the ♪ A3 · Saw · LP 1.8k readout from the artboard. Consider a perf/edit split (the dark MainViewC) so it can go full-bleed for the gig.

artboards main-view.jsx (MainViewA / MainViewC)
E

Presets & states

The preset browser is the second headline feature — it replaces the clipboard copy/paste "workaround." The prototype sketches it but stops short of the spec, and §8's required states aren't designed at all.

E1

Flesh out the preset browser to spec

High

Present: a non-functional search field, controller filters, a list, and a "Save current" button. Missing vs §6: tag, scale & favorites filters, the tiny breath-curve glyph per item, working rename / delete / favorite, and the import/export-text escape hatch that preserves the portability the clipboard gave for free.

Build the full sidebar (controller · tag · scale · favorites), make search and favorite-toggle live, add per-item actions, and keep a text import/export so presets stay shareable. This is what justifies removing the clipboard path — until it ships, don't.

spec §6 preset browser · §10 phase 4
E2

Design the eight states §8 calls out

Medium

§8 enumerates states the prototype doesn't show: empty mod matrix, matrix near-full (scrolling), idle vs active meters, MTS-ESP connected vs disconnected, preset unsaved-changes, naming/rename, and empty library. Today the matrix has a nice dashed empty-add, but the rest are undefined — and "MTS disconnected" and "unsaved changes" are exactly the moments a player needs clear feedback.

Spec each as a real state: an unsaved-changes marker on the preset nav, a disconnected treatment on the tuning chip (it's a static label now), idle-meter rest state, and an empty-library zero state. These are cheap to add and prevent silent-failure confusion.

F

Accessibility & information architecture

Small, mostly-cheap fixes that raise the floor for keyboard users, colour-blind players, and anyone reading the header for the first time.

F1

Don't encode sources by colour alone; add focus & keyboard support

High

Sources are distinguished almost entirely by a coloured dot — breath-blue vs expression-teal vs slide-purple are hard to separate for colour-blind players, and several dots are tiny. There are also no visible focus rings and no keyboard model for the sliders/matrix, so the plugin isn't operable without a pointer.

Always pair the dot with its label or CC text (the artboards already do this — keep it everywhere). Add visible :focus-visible rings, make sliders arrow-key operable, and verify text contrast on the warm surfaces, especially --muted on --panel2.

general · §10 phase 5 (accessibility)
F2

Resolve the header title ambiguity

Polish

The masthead shows the eyebrow "Vane · Performance" with an <h1> of "Breath Stage", while the preset nav beside it reads "Reedlike · Lyrical." Two competing titles — it's unclear what names the current sound.

Let the preset name be the primary title (it's what changes and what the player thinks in), demote "Breath Stage" to a section label on the Stage panel, and keep "Vane" as the quiet brand mark. One title, no competition.
